## Что такое ADR?

**Architecture Decision Records (ADR)** - это документы, фиксирующие важные архитектурные решения, принятые в ходе разработки. Каждое решение включает контекст, варианты, выбор и последствия.

**Формат:**
```
# ADR-NNN: Название решения

**Статус:** Принято / Отклонено / Устарело
**Дата:** YYYY-MM-DD
**Участники:** Имена / роли

## Контекст
Какая проблема решается?

## Рассмотренные варианты
1. Вариант А
2. Вариант Б
3. Вариант С

## Решение
Что выбрано и почему?

## Последствия
Плюсы и минусы решения.
```

## ADR-001: Выбор Django REST Framework вместо FastAPI

**Статус:** ✅ Принято  
**Дата:** 2026-01-01  
**Участники:** Tech Lead, Backend Team

### Контекст
Нужно выбрать backend фреймворк для REST API корпоративной системы управления.

### Рассмотренные варианты

**1. Django REST Framework (DRF)**
- ✅ Полнофункциональный ORM (Django ORM)
- ✅ Встроенная админка
- ✅ Большая экосистема (аутентификация, авторизация, миграции)
- ✅ Зрелая платформа (14+ лет)
- ❌ Синхронный (хотя поддерживается async views)
- ❌ Более "тяжёлый" фреймворк

**2. FastAPI**
- ✅ Async по умолчанию (высокая производительность)
- ✅ Автоматическая генерация OpenAPI
- ✅ Современный, минималистичный
- ❌ Нет встроенного ORM (нужен SQLAlchemy)
- ❌ Меньше готовых решений для enterprise (RBAC, audit)
- ❌ Молодая экосистема

**3. Flask + Flask-RESTful**
- ✅ Лёгкий, гибкий
- ❌ Слишком много нужно писать вручную
- ❌ Нет встроенного ORM

### Решение

**Выбран Django REST Framework.**

**Причины:**
1. **RBAC из коробки**: Встроенная система ролей и разрешений идеально подходит для корпоративной системы
2. **Аудит и история**: Легко реализовать audit log (created_by, updated_by)
3. **Админка**: Django Admin - бесплатная админ-панель для управления данными
4. **Миграции**: Надёжная система миграций (makemigrations / migrate)
5. **Зрелость**: Проверено годами, большое комьюнити, много библиотек
6. **Производительность достаточная**: Для нашей нагрузки (100-1000 пользователей) DRF более чем достаточно

**Компромисс:**
- Если в будущем понадобится real-time (WebSocket) - добавим Django Channels (async support)
- Для критичных по производительности endpoints можно использовать async views (Django 4.1+)

### Последствия

**Плюсы:**
- ✅ Быстрая разработка благодаря встроенным возможностям
- ✅ Лёгкая интеграция с существующими Django библиотеками
- ✅ Простота onboarding новых разработчиков (Django - популярный фреймворк)

**Минусы:**
- ❌ Чуть ниже производительность по сравнению с FastAPI (но не критично для нашего случая)
- ❌ Более "тяжёлый" стартовый проект

## ADR-002: JWT аутентификация вместо Session-based

**Статус:** ✅ Принято  
**Дата:** 2026-01-01  
**Участники:** Tech Lead, Security Team

### Контекст
Нужно выбрать механизм аутентификации для REST API. Фронтенд и бэкенд на разных доменах (CORS).

### Рассмотренные варианты

**1. Session-based (Django sessions + cookies)**
- ✅ Безопаснее (сервер контролирует сессии)
- ✅ Легко отозвать сессию
- ❌ Требует shared session storage (Redis) при масштабировании
- ❌ CORS проблемы с cookies
- ❌ Не подходит для mobile apps

**2. JWT (JSON Web Tokens)**
- ✅ Stateless (не требует хранения на сервере)
- ✅ Легко масштабировать (нет shared state)
- ✅ Подходит для SPA + mobile
- ✅ CORS-friendly
- ❌ Нельзя отозвать токен до истечения
- ❌ Payload может раздуться

**3. OAuth 2.0 (сторонний провайдер)**
- ✅ Enterprise-grade
- ❌ Избыточно для внутренней системы
- ❌ Зависимость от внешнего провайдера

### Решение

**Выбран JWT с refresh token стратегией.**

**Реализация:**
- **Access token**: 15 минут (короткий TTL)
- **Refresh token**: 7 дней (хранится в localStorage или HttpOnly cookie)
- **Алгоритм**: HS256 (симметричный)
- **Библиотека**: `djangorestframework-simplejwt`

**Стратегия безопасности:**
1. Access token короткий → минимальное окно атаки
2. Refresh token rotation → каждый refresh выдаёт новый refresh token
3. Blacklist (опционально) → отзыв refresh токенов через БД

### Последствия

**Плюсы:**
- ✅ Stateless backend → легко масштабировать
- ✅ Работает из любого клиента (web, mobile)
- ✅ Нет проблем с CORS

**Минусы:**
- ❌ Сложнее отозвать токены (нужен blacklist)
- ❌ Если токен украден - валиден до истечения TTL

**Митигация рисков:**
- Короткие TTL для access tokens
- HTTPS обязательно
- HttpOnly cookies для refresh (если возможно)

## ADR-003: Service Layer для бизнес-логики

**Статус:** ✅ Принято  
**Дата:** 2026-01-02  
**Участники:** Solution Architect, Backend Team

### Контекст
Бизнес-логика (workflow задач, approval logic) начала размазываться по ViewSets. Код становится сложным для тестирования.

### Рассмотренные варианты

**1. Fat Models (бизнес-логика в models.py)**
```python
# ❌ Плохо
class Task(models.Model):
    def submit_for_review(self, user):
        # 100 строк логики
        pass
```
- ❌ Модели раздуваются
- ❌ Сложно тестировать
- ❌ Нарушает SRP

**2. Fat Views (всё в ViewSets)**
```python
# ❌ Плохо
class TaskViewSet(viewsets.ModelViewSet):
    def submit(self, request):
        # 200 строк логики
        pass
```
- ❌ Views становятся огромными
- ❌ Невозможно переиспользовать логику

**3. Service Layer (отдельный слой)**
```python
# ✅ Хорошо
class TaskService:
    @staticmethod
    def submit_task(task, user, ...):
        # Вся логика здесь
        pass

class TaskViewSet(viewsets.ModelViewSet):
    def submit(self, request):
        task = TaskService.submit_task(...)
        return Response(...)
```
- ✅ Тонкие views
- ✅ Переиспользуемая логика
- ✅ Лёгкое тестирование

### Решение

**Внедрён Service Layer.**

**Правила:**
1. **Views** - только HTTP (валидация, разрешения, форматирование ответа)
2. **Services** - вся бизнес-логика, workflow, оркестрация
3. **Models** - только структура данных и constraints

**Структура:**
```
backend/
├── apps/
│   └── tasks/
│       ├── views.py          # Тонкие ViewSets
│       ├── models.py         # Только данные
│       └── serializers.py    # DTO
└── services/
    └── task_service.py       # ВСЯ ЛОГИКА ЗДЕСЬ
```

### Последствия

**Плюсы:**
- ✅ Код чище и понятнее
- ✅ Легче тестировать (services - чистые Python функции)
- ✅ Легче переиспользовать (из Celery tasks, management commands)
- ✅ Легче рефакторить

**Минусы:**
- ❌ Ещё один слой абстракции (learning curve для новых разработчиков)

**Альтернатива:**
- Для простых CRUD без логики можно не использовать сервисы

## ADR-004: PostgreSQL вместо MySQL

**Статус:** ✅ Принято  
**Дата:** 2026-01-01  
**Участники:** DBA, Backend Team

### Контекст
Нужна реляционная СУБД для хранения структурированных данных (задачи, проекты, пользователи).

### Рассмотренные варианты

**1. PostgreSQL**
- ✅ JSONB для гибких данных (attachments metadata)
- ✅ Full-text search встроенный
- ✅ Более строгий (лучше для консистентности)
- ✅ Лучше для сложных запросов (CTEs, window functions)
- ✅ Open-source

**2. MySQL**
- ✅ Быстрее для простых SELECT
- ✅ Популярнее (больше хостингов)
- ❌ JSON поддержка слабее
- ❌ Менее строгий (можно случайно нарушить целостность)

**3. SQLite**
- ✅ Нет сервера (файловая БД)
- ❌ Не подходит для production с множеством пользователей
- ✅ Годится для dev/tests

### Решение

**Выбран PostgreSQL.**

**Причины:**
1. **JSONB**: Для хранения flexible metadata (task attachments, custom fields)
2. **Full-text search**: Для поиска по задачам/проектам
3. **Надёжность**: Строгие constraints → меньше data corruption
4. **UUID**: Нативная поддержка UUID как primary key (security)
5. **Экосистема**: Лучше интегрируется с Django

### Последствия

**Плюсы:**
- ✅ Гибкость для будущих требований
- ✅ Надёжность и целостность данных

**Минусы:**
- ❌ Чуть сложнее в настройке для новичков

## ADR-005: React Context вместо Redux для состояния

**Статус:** ✅ Принято  
**Дата:** 2026-01-03  
**Участники:** Frontend Lead

### Контекст
Нужно управлять глобальным состоянием (auth, фильтры) во фронтенде.

### Рассмотренные варианты

**1. Redux / Redux Toolkit**
- ✅ Проверенное решение
- ✅ Мощные DevTools
- ✅ Middleware (thunk, saga)
- ❌ Много boilerplate
- ❌ Избыточно для нашего случая

**2. React Context + useReducer**
- ✅ Встроено в React
- ✅ Минимальный boilerplate
- ✅ Достаточно для простых случаев
- ❌ Нет встроенного middleware
- ❌ Performance issues при больших state (решается мемоизацией)

**3. Zustand / Jotai**
- ✅ Минималистичные
- ✅ Хорошая производительность
- ❌ Ещё одна зависимость

**4. React Query / SWR (для server state)**
- ✅ Специализация на API data
- ✅ Кэширование, refetching
- ✅ Можно совмещать с Context
- ❌ Не для всех типов state

### Решение

**Hybrid подход:**
1. **React Context** - для глобального UI state (auth, theme)
2. **Local State (useState)** - для компонентного state
3. **React Query** - в будущем для server state (опционально)

**Почему Context достаточно:**
- Простая auth (currentUser, login/logout)
- Минимум глобальных состояний
- Большинство данных - server-side

### Последствия

**Плюсы:**
- ✅ Простота (нет лишних зависимостей)
- ✅ Легче onboarding

**Минусы:**
- ❌ Если state разрастётся - придётся мигрировать на Redux

**Стратегия миграции:**
- При росте сложности → React Query для API
- Если нужна time-travel debugging → Redux

## ADR-006: Docker Compose для локальной разработки

**Статус:** ✅ Принято  
**Дата:** 2026-01-01  
**Участники:** DevOps, Backend Team

### Контекст
Нужно обеспечить reproducible dev environment для всех разработчиков.

### Рассмотренные варианты

**1. Локальная установка всех зависимостей**
- ❌ "Works on my machine" проблемы
- ❌ Сложная настройка (PostgreSQL, Python, Node.js)
- ❌ Конфликты версий

**2. Vagrant**
- ✅ Виртуальная машина
- ❌ Тяжёлый (много ресурсов)
- ❌ Медленнее Docker

**3. Docker Compose**
- ✅ Лёгкий (контейнеры вместо VM)
- ✅ Декларативная конфигурация (docker-compose.yml)
- ✅ Легко добавлять сервисы (Redis, Celery)
- ✅ Близко к production

### Решение

**Выбран Docker Compose.**

**Конфигурация:**
```yaml
services:
  db:        # PostgreSQL
  web:       # Django
  # redis:   # Будущее (для Celery)
```

**Команды:**
```bash
docker compose up -d         # Запуск
docker compose logs -f web   # Логи
docker compose exec web bash # Shell
```

### Последствия

**Плюсы:**
- ✅ Быстрый onboarding (1 команда для старта)
- ✅ Консистентное окружение для всех
- ✅ Dev/prod parity

**Минусы:**
- ❌ Требует Docker (но он уже стандарт)
- ❌ Hot reload медленнее чем native (решается volume mapping)

## ADR-007: Monolithic architecture (не микросервисы)

**Статус:** ✅ Принято  
**Дата:** 2026-01-01  
**Участники:** Solution Architect, CTO

### Контекст
Выбор между монолитом и микросервисами для MVP корпоративной системы.

### Рассмотренные варианты

**1. Microservices (Auth, Tasks, Projects, Research - отдельные сервисы)**
- ✅ Независимое масштабирование
- ✅ Технологическая гибкость
- ❌ Сложность разработки (inter-service communication)
- ❌ Distributed transactions
- ❌ Сложность деплоя (Kubernetes, service mesh)
- ❌ Избыточно для 100-1000 пользователей

**2. Modular Monolith**
- ✅ Простота разработки
- ✅ Легче тестировать
- ✅ Один деплой
- ✅ Можно выделить в микросервисы позже
- ❌ Масштабируется целиком (но это OK для нашей нагрузки)

### Решение

**Выбран Modular Monolith с возможностью миграции.**

**Принципы:**
1. Чёткое разделение на модули (`apps/accounts`, `apps/tasks`, ...)
2. Service layer для изоляции бизнес-логики
3. Слабая связанность между модулями (через сервисы, не прямые импорты моделей)

**Стратегия миграции к микросервисам:**
```
Phase 1 (Сейчас): Monolith
Phase 2 (1000+ users): Horizontal scaling (multiple instances)
Phase 3 (10000+ users): Выделить Analytics service (heavy queries)
Phase 4 (100000+ users): Полная миграция на микросервисы
```

### Последствия

**Плюсы:**
- ✅ Быстрая разработка MVP
- ✅ Простота для команды
- ✅ Меньше инфраструктурных затрат

**Минусы:**
- ❌ Все модули в одном процессе (но это OK для начала)

**Правило:** *"Start with a monolith, split when necessary"* (Martin Fowler)

## ADR-008: Two-level approval workflow (T1/T2)

**Статус:** ✅ Принято  
**Дата:** 2026-01-02  
**Участники:** Product Owner, Business Analysts

### Контекст
Нужна система согласования задач с учётом конфиденциальности и иерархии.

### Рассмотренные варианты

**1. Одноуровневое согласование**
- Все задачи → Руководство
- ❌ Перегрузка руководства
- ❌ Нет делегирования

**2. Трёхуровневое (Employee → Division → Department → Management)**
- ❌ Слишком долго
- ❌ Избыточно для большинства задач

**3. Двухуровневое с типами задач (T1/T2)**
- ✅ T2 (стандартные): Division Head → Management
- ✅ T1 (конфиденциальные): Напрямую Management
- ✅ Гибкость
- ✅ Разгрузка руководства

### Решение

**Двухуровневая схема с T1/T2.**

```
T2 (Standard):
Employee → Division Head → Management Head → Accepted

T1 (Confidential):
Employee → Management Head → Accepted
```

**Обоснование:**
- T1 для чувствительных задач (HR, финансы)
- T2 для обычных (технические, исследования)
- Division Head может отклонить задачу на T2 → экономия времени руководства

### Последствия

**Плюсы:**
- ✅ Делегирование рутины
- ✅ Быстрое согласование T1
- ✅ Контроль руководства сохранён

**Минусы:**
- ❌ Чуть сложнее workflow (но оправдано)

## ADR-009: Soft delete вместо физического удаления

**Статус:** ✅ Принято  
**Дата:** 2026-01-02  
**Участники:** DBA, Compliance Officer

### Контекст
Нужно удалять задачи/проекты, но сохранять audit trail.

### Рассмотренные варианты

**1. Физическое удаление (DELETE FROM)**
- ❌ Невозможно восстановить
- ❌ Потеря audit trail
- ❌ Нарушение compliance требований

**2. Soft delete (поле `deleted_at`)**
- ✅ Можно восстановить
- ✅ Audit trail сохраняется
- ✅ Соответствие GDPR (right to deletion - можно реализовать отдельно)
- ❌ Сложнее запросы (нужен фильтр `deleted_at IS NULL`)

**3. Архивация (отдельная таблица)**
- ✅ Основная таблица чистая
- ❌ Сложность миграции данных
- ❌ Дублирование схемы

### Решение

**Soft delete для всех критичных сущностей.**

**Реализация:**
```python
class BaseModel(models.Model):
    deleted_at = models.DateTimeField(null=True, blank=True)
    
    objects = ActiveManager()  # Только активные
    all_objects = models.Manager()  # Все (включая удалённые)
    
    def soft_delete(self):
        self.deleted_at = timezone.now()
        self.save()
```

### Последствия

**Плюсы:**
- ✅ Compliance с аудитом
- ✅ Возможность восстановления

**Минусы:**
- ❌ Увеличение размера БД (но disk space дешёвый)
- ❌ Нужны background задачи для архивации старых записей
